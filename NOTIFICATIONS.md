# LinkBarangay notification implementation and deployment

This change extends the existing `lb_notifications` stream. Database triggers create persisted notifications in the same transaction as the source event; the browser reads them and marks them read. Roles remain `resident`, `admin`, and `worker`, with the existing worker functions and authorization rules.

No live Supabase project was connected or changed during this work. References to earlier live deployments in `SYSTEM_AUDIT.md` or the old runbook describe previous work and are not verification of migration 0015.

## Implementation

- One `NotificationsProvider` supplies the shell and inbox. Its account-specific store serializes fetches and read mutations, discards responses from old account lifecycles, coalesces repeated operations, and preserves loaded history when a refresh fails.
- Unread counts come from an exact database count across the complete history. Header, sidebar/mobile sidebar, and account menu share the same badge: zero is hidden, 1–99 display literally, and 100+ displays `99+`. Accessible labels include the actual count.
- History loads newest first in pages of 50, with a `(created_at, id)` keyset and retained PostgreSQL timestamp precision. Duplicate rows merge by notification ID. Opening the inbox does not mark anything read.
- Successful individual/all-read RPCs update shared state immediately, then reconcile with the database. Read time is generated by PostgreSQL. Requests carry the expected user identity so a stale operation cannot act on a newly signed-in account.
- One account-filtered Realtime channel receives inserts and read-state updates. Reconnect, browser focus, visibility, and online events trigger reconciliation. While visible and online, failed Realtime connections use a 30-second fallback; connected channels reconcile quietly every two minutes. Timers, listeners, and channels are removed on cleanup.
- The inbox preserves the existing design and adds read controls, action pending states, icons, meaningful titles/messages, existing localized date formatting, loading/empty/error/retry states, and older-history loading.
- Destinations are an explicit allowlist of existing views, never arbitrary URLs. Opening a related request, job, or appointment first performs an ordinary authenticated RLS-protected lookup. A resident opens a read-only preview of their own appointment in the inbox, without access to secretary scheduling controls. Own-jobs and dispatcher-assignments module links also require their existing permissions. Deleted records or changed access produce a message without removing history. Legacy notifications containing only `request_id` still open requests. Field job details fetch the assignment directly, so an older job does not depend on the first 100 jobs being listed.
- Account profile refreshes track role/status changes used by navigation and guard asynchronous account switches. RLS remains authoritative.
- Historical assignments remain visible without contributing to actionable field/dispatcher workload. Current responsibility checks include the newest assignment across all statuses, the request's current assignee, department, and workflow status. Reopening/rerouting releases the former field responsibility.
- Assignment forms initialize deadlines in browser local time, preventing the former UTC-to-local shift when an unchanged deadline is submitted.
- Request transitions lock their source row and return the existing result on an identical retry. Overlapping status actions therefore create one committed workflow event. Unknown permissive notification policies cannot bypass the restrictive own-recipient guard; anonymous table and column SELECT grants are removed.

## Event-to-recipient coverage

All worker recipients below must be active and belong to the request's barangay, department, or actual assignment as stated. Notifications linking to request details recheck the recipient's current request-access relationship. Former personnel receive only generic responsibility-ended notices without the new scope's information. The actor is excluded except for a resident's submission acknowledgment and direct account-access notices. Administrators are globally authorized by the existing model; this change does not introduce administrator scope fields.

| Existing event / source | Recipients and reason | Destination |
|---|---|---|
| Resident submission (`app_submit_resident_request`) | Submitting resident receives acknowledgment; same-barangay secretaries and officers receive intake work | Request |
| Secretary walk-in encoding | Same-barangay intake secretaries/officers other than the actor; no fictional resident account is created | Request |
| Anonymous/unscoped submission, or submission without an available intake team | Scoped intake when a barangay is present; active administrators when no barangay or no active secretary/officer can handle intake | Request |
| Submitted → verification; reopened request | Owner and same-barangay officers/captains who review the verification queue; assigned field personnel when still relevant | Request / assigned job |
| Additional information requested | Owner and relevant current assignee; request message contains the requested update | Request / assigned job |
| Resident information reply (`app_reply_info_request`) | Same-barangay secretaries, officers/captains, and the requesting staff member who must resume review; actor excluded | Request |
| Verification / forwarding / assigned status | Owner; same-department dispatchers when the request enters their workflow; officer when verified but no department is assigned | Request |
| Field assignment (`app_assign_field`) | Assigned active field worker in the assignment's department; resident receives the request assignment event | Job / request |
| Assignment reassignment, schedule/deadline, dispatcher instruction changes | Relevant assignee; previous assignee receives a generic reassignment notice without the new assignee's details | Job / own jobs module |
| Reopening or routing to a different department releases the assignment | Former field worker receives a generic notice; former department dispatcher also receives a generic reroute notice | Jobs / assignments; no newly restricted record link |
| Field acceptance / work started | Owner and same-department dispatchers responsible for progress | Request |
| Assignment declined | Owner and same-department dispatchers who must reassign; the old explicit decline fan-out is replaced to avoid overlap | Request |
| Field job progress / staff comment (`app_update_job_progress`, `app_add_comment`) | Owner, relevant current field assignee, requesting staff member when applicable; department dispatcher for a current assignee's progress comment | Request / job |
| Resident comment (`app_add_comment`) | Current intake team while submitted/under verification/waiting for information; officer/captain while awaiting inspection; current assignee, requesting staff member, and department dispatcher where relevant | Request / job |
| Work completed / inspection requested | Owner, department dispatcher, and same-barangay officers/captains responsible for review | Request |
| Resolved, closed, rejected | Owner and relevant current assignee; department dispatchers; same-barangay captain for resolution/rejection | Request / job |
| Escalation (`app_escalate_request`) | Owner, same-barangay officers/captains, department dispatchers, current assignee, and administrators for intervention | Request / job |
| Resident supporting/reply document metadata committed | Same-barangay secretaries/officers who review documents | Request |
| Current assignee completion document metadata committed | Same-department dispatchers who review completion | Request |
| Appointment created, rescheduled, purpose/instructions changed, completed, cancelled, no-show, or deleted | Affected resident and same-barangay secretaries other than the actor; previous resident gets a generic notice if the appointment is reassigned | Staff appointments module; resident's own read-only appointment preview; unavailable/deleted appointments retain informative history |
| Account created | Affected account; a pending account also alerts active administrators for approval | Own profile / user management |
| Account activation, suspension, approval, role/function, barangay, or department change | Affected account and other active administrators for access-management review | Own profile / user management |
| Assigned field personnel's role/function, active status, or department changes | Dispatchers in the department of that person's active assignments, with a generic notice to review reassignment; no new department details disclosed | Assignments |
| Significant settings, routing, SLA, required-document, category availability, barangay/department availability changes; reference creation/deletion | Other active administrators with configuration access | Relevant existing configuration module |

Resident records and personnel directories are read-only views over profiles/assignments. Their meaningful writes are covered by the account and assignment events above. Searches, navigation, report viewing, audit viewing, cosmetic profile edits, routine configuration label edits, and work-photo uploads do not create notification noise. The existing application has no separate approval-record system, standalone intake-task table, arbitrary department inbox, or assignment cancellation status; notifications do not invent those workflows. Appointment updates are covered at database level even though the existing UI currently exposes creation and status changes rather than a rescheduling editor.

Notifications describe completed source transactions. A failed/rolled-back operation delivers no notification. Deduplication keys pair each source event with its recipient, so overlapping delivery paths for one event cannot create duplicate rows; repeated, distinct workflow events remain eligible.

## Deploy to an existing Supabase project

1. Confirm the database has the schema from migrations `0001`–`0014`, including worker functions, pending approval, and sign-up barangay handling. Reconcile migration history with actual schema first if earlier files were applied through SQL Editor. Do not reset the project or rerun historical data conversions blindly.
2. First run **`supabase/verification/0015_preflight.sql`** in SQL Editor. It is read-only and checks the required tables, role model, function definitions, nullable notification relationship, policies and publication. Resolve any reported schema differences before proceeding. Then apply the complete **`supabase/migrations/0015_unified_notifications.sql`** once through the project's existing migration process or Supabase SQL Editor. It runs in a transaction, adds nullable metadata and useful indexes, replaces delivery logic, changes the notification request FK to `ON DELETE SET NULL`, narrows read access, and installs the read RPC. Existing notification rows remain intact. Plan for normal DDL locks on the notification table. The migration validates the workflow definitions it patches; if it reports an unknown assignment/comment definition, the transaction stops and the deployed RPC must be reviewed against the archive before retrying. Do not remove that guard or skip part of the transaction.
3. Deploy the updated frontend after the migration. Copy `.env.example` to `.env.local` and supply that project's URL and publishable key. Never expose a service-role key to Vite. No new Edge Function or client-side notification insertion is needed.
4. Verify Realtime publication membership and INSERT/UPDATE publication. The migration adds `lb_notifications` if the `supabase_realtime` publication already exists. If the publication is absent, enable the project's Supabase Realtime replication setup in the Dashboard and add this table. The frontend fallback still reconciles while Realtime is unavailable.
5. The migration sends PostgREST a schema-cache reload notification. If the new read RPC is initially missing from the API, reload the schema cache through normal Supabase operations and retry. The UI reports a migration-required error rather than falling back to unsafe writes.
6. Run the manual checks below with scoped test accounts. None of these deployment steps were performed against a live project in this session.

### Historical archive caveat for a fresh project

The uploaded archive's `0004` already contains canonical `worker_function` queries. Migration `0007` nevertheless requires finding and replacing their legacy forms, and raises `No known role query found ... refusing incomplete role migration` on that already-updated baseline. Consequently, an unmodified clean replay of the archived migration history is not a verified installation path. This pre-existing issue is not repaired by changing previously applied migrations.

The isolated database test harness explicitly restores just those legacy function strings with `supabase/tests/legacy_role_fixture.sql` immediately before running the unchanged `0007`, reproducing the assumptions of the historical role migration. It then runs all later migrations, including the actual unmodified `0015`. This fixture is test setup only: **never run the test bootstrap or compatibility fixture on a deployed project**. For an empty project, use the guarded `supabase/bootstrap/0007_fresh_baseline.sql` initializer instead of archived 0007, following `SETUP_GUIDE.md`. It validates the canonical workflow definitions and applies the remaining 0007 constraints/guards/grants; it refuses populated application databases. This path passed the 112-assertion PostgreSQL suite using `LB_TEST_CANONICAL_BOOTSTRAP=1 npm run test:db`, without the legacy-role string fixture. Existing deployments must continue to follow their actual migration history.

### Manual acceptance checks after deployment

Use two barangays and two departments, including one unrelated account of each relevant role. Use separate browser profiles for different accounts and a second tab for the same recipient.

1. Submit as Resident A. Check A's acknowledgment and the correct intake workers' persisted rows; Resident B, other barangay workers, and routine administrator inboxes should receive nothing. Verify anonymous reports without a barangay reach intervention administrators.
2. Verify, request information, reply, attach a reply document, forward, assign a field worker, accept, add progress, decline/reassign where applicable, complete, inspect/resolve, close, reopen, reject, and escalate. Compare each event's recipients with the matrix and confirm unrelated accounts receive no rows. Failed/unauthorized actions must create neither workflow changes nor notifications.
3. Create and update an appointment as secretary. Check the affected resident and relevant peer secretary, including cancellation and status changes. Confirm the resident can inspect their own appointment in the inbox preview and does not gain secretary-module permission or scheduling controls. Attempts to link another barangay's resident/request must fail.
4. Create/approve a pending worker account, change role/function/scope, suspend, and reactivate using existing administrator flows. Verify affected-user and peer-admin notices. A suspended/inactive account must receive no notification read access; a persisted suspension notice becomes readable only after access is restored.
5. Change a significant routing/SLA/availability setting. Verify other administrators receive it; cosmetic label edits and read-only views should not create routine notifications.
6. Keep the inbox open in two tabs. Trigger an event from another account and check history/bell updates without refresh. Read one in the first tab and confirm the second tab reconciles. Opening the inbox alone must leave all unread states unchanged.
7. Check badge counts 0, 1, 5, 25, 99, and 100+ against `count(*) where is_read = false`; load more than 50 rows and confirm no missing/duplicate history. Mark one/all read, navigate away, refresh, sign out/in, and verify persisted state.
8. Disconnect/reconnect the network, background/refocus the tab, and temporarily disable Realtime for a test project. Verify catch-up and fallback polling; inspect that only one notification channel exists per signed-in application instance and no old-user channel remains after account switching.
9. Rapidly click read/open controls while switching accounts. No prior-account list/count, stale navigation, or wrong-account read mutation should apply. Deleted/inaccessible destinations should show the useful error without crashing.
10. Using the ordinary authenticated API role, attempt to read another user's rows, insert a forged notification, change ownership/content/destination, update read state directly, mark another user's notification read through the RPC, and call the RPC with another expected user ID. Read results must be scoped; forbidden writes must fail or affect zero rows as appropriate. Recheck department/barangay and field assignment separation.

## Security and operational limits

- An active authenticated user can select only their own notifications. Direct API INSERT/UPDATE/DELETE and column-write grants are removed. Only the narrow server RPC sets read state, with server timestamps, current-account validation, and active-status checks. Private emission/access helpers are not executable by API roles.
- Assignment operations validate the active field account, department, and current request assignment before changing work. Stale historical assignments cannot continue producing job updates after reassignment. Repeating the same pending assignment operation does not create another assignment or notification; changed assignees receive the appropriate new/previous-worker notices. Appointment relationship validation rejects cross-barangay resident/request links before notification delivery.
- Suspension notices are persisted for the affected account, but that account cannot read its history while inactive. This preserves the existing access restriction rather than granting an exception for notifications.
- Notification content avoids copying sensitive account details, appointment notes, or attachment contents. Request remarks are delivered only to authorized recipients at event time. Historical messages are the recipient's retained history; an inaccessible destination never grants new record access.
- Existing records are retained and do not receive fabricated backfill events. Events committed before this migration that previously had no delivery are not retroactively reconstructed.
- Database notification insertion is transactional: an unexpected delivery error fails the whole source transaction rather than saving an event with incomplete delivery. Monitor database logs and investigate workflow errors instead of suppressing them.
- Notifications are an in-app persistent history and Realtime stream. Email, push, SMS, background-browser delivery, time-based overdue detection without an existing source event, and missing business workflows are not introduced.
